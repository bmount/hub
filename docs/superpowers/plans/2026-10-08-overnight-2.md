## Tasks, in order

### N1. The in-context MCP Playground
- Lives at `/playground` on an organization's host, signed in.
- Lists the MCP tools as an assistant connection would see them. You choose the scope set, read or read and write.
  The list is computed by the same policy as `/mcp`: `exposedVerbs(role, scopes)`.
- Runs a tool through the same code as `/mcp` (`callTool`): same input checks, same rendering, same audit.
- Shows the JSON-RPC request and response, the text an assistant would read, the structured result, and the time.
- **Isolation, the core of the task, each property with its own test:**
  - A call runs only in the organization of the host it was made on. No parameter can name another organization.
  - Authority is the signed-in person's current role. Scopes can only narrow it. A tool outside the chosen scopes is
    refused exactly as `/mcp` refuses it.
  - Only same-origin POSTs with a valid form token are accepted (no cross-site use of the session cookie), and only
    from a browser session. Bearer, agent and OAuth credentials can't use the Playground.
  - Every call is recorded like an MCP call, marked as from the Playground, with the session id.
  - Results go through the same do-not-follow data notes, and secrets never appear.
  - Archived organizations, removed memberships and helper identities are refused.
- Reachable from navigation for members (Admin and People link to it), and from `/skills/start-here`.

### N2. Auth stress suite (automated)
These run in the normal test suite, against the real `/mcp` and OAuth endpoints:
- a token used against a different organization's `/mcp`;
- a token whose grant was revoked, expired, or belongs to an archived or deleted organization;
- scope escalation: a read grant calling write tools, or asking for scopes it never had;
- a role downgraded or a membership removed mid-session: tools vanish without re-consent;
- refresh-token replay revokes the grant;
- per-grant rate limits;
- no tool result or error ever contains a credential-shaped string;
- Playground isolation from N1, repeated under the same harness.

### N3. Mail to structure, for the PriceBench threads (the owner's first real use)
- On a mail page, "Propose work" asks the `deep` model to read the message as evidence and propose wishes, snags,
  errands and calls. Each proposal has a title, a body, and the quoted sentence it came from.
- A member confirms, edits, or drops each one. Confirmed items are filed with `work.create`, with `source_kind`
  mail, `source_ref` the mail id, and the quote.
- Over MCP: `mail_propose_work` returns proposals only (read scope). Filing stays with `work_create`, so an assistant
  confirms in the open.
- The model's output is treated as data and is never executed. Proposals are validated against the work kinds and
  length limits.
- Tested with a stand-in model.
