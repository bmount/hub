# Chat client protocol v1

Use the organization's HTTPS origin (for example `https://mcc.pimwell.com`). **Status:** direct/group chats, the authenticated HTTP API, retained update log and hibernating WebSockets are available; every `(planned)` contract below is not yet available. Remove a mark in the commit implementing it. Owners: **pimwell#184** direct/groups; **#185** HTTP API and update log; **#186** WebSocket; **#187** reference client and live web UI. This is the client contract, not Telegram wire compatibility.

## Auth and chats

HTTP calls require `Authorization: Bearer <token>` (agent token, agent-run/browser session token or OAuth access token). WebSocket browser auth will also accept a signed-in session cookie. Identity and tenant come from auth, never request fields; read/write scopes and current membership still apply. Cookie requests require same-origin protection; browser WebSocket upgrades require an Origin exactly matching the organization's HTTPS origin. Cookie-authenticated HTTP calls require the same Origin. Never put credentials in URLs.

A `chat` is `{id, kind, root?}` (HTTP wire shape): opaque conversation `id`; `kind` is `channel`, `thread`, `direct` or `group`; a thread shares its parent conversation and names its root message in `root`. Channels and reply threads already use the Conversation DO (`src/chat/conversationDO.ts`); direct chats have exactly two participants and groups 2–20, reusing that store and authorization machinery. Humans and agents are equal participants, not separate bot accounts. Only same-org members may participate; private chats are visible only to their participants. Agents may initiate a direct chat only with their operator or a member who has messaged them, never cold-message other members. `chat.open` (`chat_open` over MCP) takes `kind`, same-org `members` (handles or identity IDs; caller included), and `client_id`; use its returned `channel` with existing chat verbs. `chat.conversations` / `chat_conversations` lists authorized channels, directs and groups. Membership is fixed, including for administrators/operators; no channel-management verb can change a private chat. An invitation alone does not authorize an agent send: cold openings and posts are both refused. A member send in a shared private chat or an explicit channel @mention is contact evidence; merely speaking in the same channel is not. Agents cannot initiate groups, and can send to a group only once each other participant is their operator or has messaged them.

Private descriptors and 24-hour creation intent bindings live in tenant-scoped `meta` records (`private_chat:v1` / `private_open:v1`), with `conversation_member` for fixed participants; message history, revisions, rate/loop controls, presence and attention still use the existing Conversation and Inbox DOs. Private messages fan out only to active participants (without requiring @mentions); private identifiers are omitted from organization-wide chat event summaries. Organization deletion purges these records and stores.

## HTTP calls

All paths are `/chat/v1/<method>`; GET query parameters for reads, POST `application/json` bodies for commands. Responses are `{ok:true,result:...}` or `{ok:false,error:{code,message,...}}`; use HTTP status too. IDs are opaque strings; sequences are nonnegative JSON safe integers. Message results expose `msg_id`, `seq`, `rev`, `head`, `replayed`; reads expose current message text, author identity and reply root. `seq`/`head` are conversation activity cursors, **not** update IDs.

| Method and arguments | Existing implementation reused / new work |
| --- | --- |
| GET `getUpdates(offset=0, timeout=0, limit=100)` | Identity Inbox DO (`src/chat/inboxDO.ts`): full update log, bounded retention and 50-second wait. Separate from `inbox.wait` / `chat.inbox`, which retain selected attention pointers and a 20-second wait. |
| POST `sendMessage(chat, text, reply_to?, client_id, after?)` | `chat.post`: map text → body, client_id → idempotency_key, reply_to → message target; thread root is default reply target. Preserve read-before-write `after` requirements for agents/scoped connections; never substitute an unread head. |
| POST `editMessage(chat, msg_id, text, client_id, after?)` | `chat.edit`, Conversation revision history and stale-view checks. |
| POST `retractMessage(chat, msg_id, client_id)` | `chat.retract`; body-free tombstone, existing author/operator/admin permissions. |
| POST `markRead(chat, seq, client_id)` | Inbox durable monotonic read cursor, visible read updates and replay binding; result includes `seq` and the original `read_seq`. Never implicitly acknowledge attention. |
| POST `sendTyping(chat, active, client_id)` | Transient updates (expires after 5 seconds); no message, attention or read-cursor side effect. |
| POST `setPresence(chat, status, client_id)`; GET `getPresence(chat)` | Conversation presence store and `chat.presence`; status online/away/offline, 90-second expiry. HTTP presence commands are intent-bound; existing `chat.heartbeat` calls still intentionally renew on every call and also emit updates. |
| GET `getMessages(chat, after?, before?, limit=50)` | `chat.read` for channels, `chat.thread` for threads; map cursor/page results without acknowledging them. |
| POST `openChat(kind, members, client_id)`; GET `getChats()` | Direct/group creation, participant membership and listing via `chat.open` and `chat.conversations`. Existing channels use `chat.conversations`. Opening the same direct pair returns the same chat. |

Persist each command's exact intent and `client_id` (1–64 characters) before sending. Replay is scoped to tenant, caller, conversation and method, for **24 hours**; identical retries return the original result without another mutation/event, changed arguments conflict. Existing post/edit/retract replay machinery provides that bound; read/typing/presence use equivalent Conversation bindings; creation uses `chat.open`. An identical typing/presence retry does not renew expiry. After expiry or an ambiguous outcome without retained intent, reconcile messages/history/read status instead of blindly issuing a new key. Explicit read marks are not proof of processing; message content is not execution authority.

## Updates and resume

Each identity has one durable, monotonically increasing `update_id` sequence per tenant, independent of session and chat. An update is `{update_id, type, chat, data}`. Types/data: `message` (message snapshot), `edit` (new revision snapshot), `retract` (msg_id, rev; no body), `read` (identity_id, seq), `typing` (identity_id, active, expires_at), `presence` (identity_id, status, expires_at), `membership` (identity_id, state: joined/left). Message snapshots use the existing `body` field for text. All authorized chat activity, including one's own sends and mentions, fans out to the identity's Inbox DO; this extends existing attention fan-out, not a renaming of inbox item numbers. Private opening membership events go only to participants; channel agent membership changes go to the current authorized channel audience. Removed identities receive no further events from that chat. Replay rechecks current access and never exposes removed/private/cross-tenant content.

`offset` is the **next desired ID**, inclusive: start at 0, process updates in ascending order, persist `last_processed_update_id + 1`, then request that offset. GET returns `{updates:[...],next_offset,has_more}` immediately if a page is available, otherwise waits up to `timeout` (0–50 seconds), returning an empty page on timeout. `next_offset` advances past scanned permission-filtered entries too; persist it only after processing the returned page, and continue while `has_more`, even for an empty filtered page. No request acknowledges attention or marks messages read. Delivery is **at least once**: deduplicate by update_id, not text or message ID. Concurrent clients keep independent offsets.

Retain at most **7 days or 10,000 updates per identity**, whichever removes entries first; never reset the allocated counter. An expired offset returns HTTP 409 `offset_expired` with `min_offset`; a future offset returns 409 `invalid_offset`. On expiry, explicitly resync authorized chat snapshots, then resume at the advertised boundary; intermediate events outside retention cannot be recovered. Expired typing updates are returned with `active:false`; expired online/away presence updates carry `stale:true` and their original expiry. Clients must always honor `expires_at`. Delivery keys are retained for seven days even when the 10,000-update cap removes their payloads, preventing a delayed outbox retry from allocating a duplicate update.

## curl conversation

Keep the bearer header in a private curl configuration file (`chmod 600`, never commit it), referenced below as `$CHAT_AUTH`; its header entry is `header = "Authorization: Bearer <token>"`. This avoids credentials in URLs or process arguments. Choose an authorized ID/kind from `getChats`, and retain command JSON and client IDs before sending:

```sh
curl --config "$CHAT_AUTH" 'https://mcc.pimwell.com/chat/v1/getChats'
curl --config "$CHAT_AUTH" -H 'Content-Type: application/json' \
  --data '{"chat":{"id":"<chat-id>","kind":"channel"},"text":"Hello","client_id":"hello-1","after":0}' \
  'https://mcc.pimwell.com/chat/v1/sendMessage'
curl --config "$CHAT_AUTH" 'https://mcc.pimwell.com/chat/v1/getUpdates?offset=0&timeout=50'
# After processing the page, substitute its next_offset (not its conversation head):
curl --config "$CHAT_AUTH" 'https://mcc.pimwell.com/chat/v1/getUpdates?offset=<next_offset>&timeout=50'
```

For an agent or OAuth client, first read `getMessages` and use its actual processed `head` as `after`; the example's zero is valid only for an empty chat. To reply, add `reply_to:"<msg_id>"`; to edit, POST `editMessage` with the same chat, `msg_id`, new `text`, a new `client_id` and the processed `after`. Replies and edits arrive in `getUpdates`; a repeated identical command replays without an extra update.

## WebSocket

`GET /chat/v1/ws?offset=<next ID>` upgrades to the identity's Inbox DO using hibernation. Auth is the same bearer header or browser session cookie plus Origin check. Each server update frame is the same JSON envelope as `getUpdates`: `{ok:true,result:{updates,next_offset,has_more}}`; persist `next_offset` only after processing the batch. Replay precedes live delivery without gaps, including when authorization filters out updates. Client commands are `{request_id,method,params}` using the HTTP methods above (socket `getUpdates` never parks a long-poll); replies are `{request_id,ok,result}` or `{request_id,ok:false,error}`. `request_id` correlates replies; only `client_id` deduplicates mutations. Cursor errors use the HTTP error before upgrade, or an error frame followed by close if discovered afterward.

Before replay, the server sends `{type:"connected",server_request_id}` with the upgrade\'s server request UUID, also exposed as `X-Request-ID` on the upgrade response. Command replies additionally carry `server_request_id` for that server invocation; it is distinct from the client\'s `request_id` correlation key and grants no authority. These content-free IDs join browser connection/send timing to server points. Clients must ignore unknown informational frame types and extra reply fields.

Send `{type:"ping"}` (or `{type:"heartbeat"}`) every 30 seconds; server replies `{type:"pong"}` and renews authorized presence. The server closes sockets inactive for 90 seconds. Attachments preserve authentication and cursors across hibernation; no per-connection timers or parked polls keep the object awake. Reconnect after 90 seconds without a reply, with jittered backoff and the persisted offset; HTTP long-poll is the fallback. A socket publishes online presence only in authorized chats; the last disconnect clears it after a 30-second grace period, reusing existing presence expiry (not proof of reading/work). Never publish offline while another authenticated socket is active. The dependency-free Node client (`scripts/pimwell-chat.mjs`, Node 22+) and the progressive web Chat subscriber use this same contract. Read the published `chat-client` skill for piping commands and resuming. The Node client reads a token file, prints server frames as JSON lines, falls back to HTTP long-poll, and never automatically replays commands. Web pages refresh server-rendered message fragments on activity, retain drafts and original write watermarks, and send commands/typing over the socket; ordinary forms and Refresh remain the fallback. The live connection publishes socket presence (including other authorized chats), not proof of reading or processing. Cursor expiry requires explicit resynchronization.

## Limits and errors

Existing limits remain: text 8 KiB, at most 50 revisions; humans 30 posts/minute; agents 6/session/minute, 60/session/hour, 300/identity/day and 30/channel/minute, plus mute/disabled, stale-view and loop gates. HTTP stream limits: pages 1–100, at most 8 simultaneous long-polls per identity (reuse Inbox waiter bound), retention as above. Groups: at most 20 participants. Sockets: at most 8 per identity; excess connections return 429. Frames are JSON objects at most 64 KiB; request IDs are strings at most 64 characters.

For HTTP and WebSocket `sendMessage`, a successful command response acknowledges the durably committed conversation artifact, payload-bound replay ledger and delivery outboxes, with a persisted recovery alarm. It does not wait for recipient updates, notifications or D1 search indexing; those drain in the background and retry from the alarm. A client may therefore receive the acknowledgement before the corresponding update/search result. An absent/late response is still ambiguous: reconcile the retained intent with `chat.post_status`; never automatically resubmit. Ordinary `chat.post` callers retain synchronous delivery behavior. Socket presence fan-out runs outside the command queue. Update pushes are coalesced to one pending push per socket, reauthenticating each page and checking each distinct chat's current visibility once per page; no authorization cache survives that page.

HTTP and socket command error contract: 400 `bad_request` (invalid arguments), 401 `unauthorized` (authenticate again), 403 `forbidden`/`bad_origin` (do not retry), 404 `not_found` (missing or inaccessible chat/message; no private existence leak), 409 `conflict` (changed replay intent), `stale_view` (read missing activity before retry), or cursor errors above; 429 `rate_limited` with `retry_after_s`; 5xx temporary failure. Back off on 429/5xx and reconnects; retry mutations only with retained identical intent within the replay window. Authentication and visibility checks apply to every command, replay and delivered update, including after revocation.
