# Git history rules

Every push to a Pimwell repository, project or `agent-src` alike, goes through `artifactPush` (`src/code/artifactPush.ts`). It stages the pack in a private, repository-owned validation cache, checks each ref update, and only then publishes. Cloudflare Artifacts itself would accept any rewrite, so these rules live in the push path:

- **Branches only move forward.** An update must contain the old tip in its history. A rewind or divergent update is refused, and the pushed commits are kept under `refs/ardi/forks/…` so nothing is lost.
- **Tags never change** and can't be deleted.
- **Any branch but the default one can be deleted**, merged or not. The push log (`git_push`) keeps the deleted tip, so a branch deleted by mistake can be pushed back while its commits still exist somewhere. Deleting the default branch is refused.

Delete a feature branch once it is merged or abandoned: `git push origin --delete <branch>`. Small changes can go straight to `main`.

A refused update gets `ng <ref> <reason>` in Git's report; the rest of the push still applies unless the client asked for an atomic push. The rules are in `src/code/gitHistory.ts` and are tested in `test/git-history.test.ts` and `test/artifacts-git.test.ts`.

## Search snapshots

Repository search reuses the hub request's live authorization, not a cached grant or a second Git credential. Verified snapshots are immutable and keyed by storage account, tenant, project, physical repository and commit. An immutable commit hit needs no upstream metadata, log or pack request. A symbolic revision still reads fresh Git refs before looking up the snapshot; branch moves are never hidden by a ref TTL. HEAD is read from the advertisement. On a miss, storage ownership is checked and a shallow pack supplies the commit and files; decoding verifies the requested commit exists, without a separate log request. Binary, oversized-file, path, ordering and match-limit rules are unchanged.

Measure completed `repo.search` calls (including fresh request authorization and response consumption) separately from local `searchFiles` CPU. For reproducible small-repository acquisition measurements, use an owned `tmp-` repository with one UTF-8 `fixture.txt`: `needle fixture <revision>\n` followed by 100 `ordinary text\n` lines, about 1.4 KB. Publish distinct commits, then search each commit exactly once to measure cold acquisition; repeat the same commits for warm snapshots. Also measure a symbolic branch separately, since it intentionally pays for a fresh advertisement. Check the exact matching line and searched-file count on every response. Run at least 100 calls per phase, report nearest-rank p95, and remove the fixture afterward. These timings do not establish a bound for large repositories or other caller locations.

## Large pushes and recovery

Initial pushes retain original history, vendored files and tags; there is no squash or stripped-source requirement. The HTTP replay limit is 100 MiB (commands plus compressed pack), not the unpacked checkout size. A ~65 MiB, 11,999-object, 33-commit repository fits. Ancestry validation permits at most 512 log requests; metadata validation has a 900-call ceiling. Larger histories can be sent in fast-forward batches without changing commit IDs.

The first push creates an owned validation cache by forking the existing repository. New caches use a random physical storage name reserved atomically in the private D1 `artifact_fork_ownership` ledger, scoped to storage account, namespace, canonical repository and tenant/project description. The reservation and the push's physical shadow mapping are durable before the fork request, so a lost creation response does not lose cleanup authority. Concurrent first pushes select the same reservation. Existing readable deterministic caches are reused without moving their objects; unreadable legacy caches are not granted guessed ownership. Later pushes reuse its objects, not its mutable canonical refs: each attempt stages under unique private `refs/tags/pimwell-stage-<push UUID>/<index>` refs. Native Git verifies the incoming pack there; ancestry is checked by object ID, and publication still sends the client's original old-OID/ref commands to the canonical repository. Concurrent attempts cannot overwrite each other's validation refs, and only canonical old-OID compare-and-swap can publish. Access is checked again before publication. Cache ownership and storage mapping are verified on every use, including readback after racing first-fork creation. Internal validation advertisements skip HEAD normalization and its unrelated metadata requests.

Private validation refs remain reachable so future thin packs can use previously published objects, including after canonical branch deletion. They are not exposed through canonical Git/ref APIs. Successful/refused replay packs are discarded as before; routine cleanup never deletes a ready shared object cache. Project and organization deletion discard replay data without treating a shared cache as a per-attempt temporary fork; deleting its owning repository deletes the cache too, after checking both ownership markers. A cold cache still pays the initial copy cost; large initial upload/pack processing is not made constant-time by cache reuse.

Failed/incomplete fork cleanup treats only the exact upstream HTTP 409/code 10303 metadata response as a possible incomplete repository. Deletion then requires matching durable creation evidence; other errors, mismatched readable ownership and mismatched storage mappings remain fail-closed. Unique temporary stages are reserved only after checking their UUID target is absent; successful fork receipts also persist ownership. Cleanup accepts asynchronous HTTP 202/204 acknowledgements, retains a deletion tombstone across retries and removes it only after confirmed 404. Tombstones prevent cache reuse while deletion is pending. Scheduled cleanup independently scans old failed reservations/tombstones, including those without replay objects or surviving project rows, but protects recent attempts and unknown/publishing recovery records. Once a cache has been verified usable, routine cleanup leaves it alone. Project/organization deletion can delete its owned cache and also cleans temporary forks whose replay key is already empty.

Fork requests have a 90-second deadline; other REST requests have a 20-second deadline. Native Git requests, including their status-body reads, have a 120-second deadline. All upstream work for a push shares a five-minute budget. Uploads, storage and cleanup also consume time; clients should not impose a 90-second total timeout on a large initial push. Upload completion alone is not publication evidence.

Transient upstream failures return a Git `ng` report naming the phase and push ID, rather than misleading success. A failure before publication records `refused`; a lost publishing response records `unknown` and retains the replay pack and private validation refs. Pimwell does not blindly retry a write with an ambiguous result. Before retrying, run `git ls-remote <remote>`, compare **each** branch/tag ID to the intended IDs, then fetch. If the IDs already match, publication succeeded despite the lost response; otherwise retry from the advertised tips without force-pushing. `repo_branches`, `repo_log` and `repo_file`, plus a fresh clone, provide independent readback. The durable `git_push` row records outcomes and the push ID for operator diagnosis; unknown/publishing records are never removed by routine staging cleanup.
