# MCP: current exposure and security contract

## Project connections

An active project exposes `https://<org>.pimwell.com/p/<project>/mcp` (or `/p/<namespace>/<project>/mcp` for a namespaced project); its project page has a copy button and connection instructions. The path endpoint avoids introducing paid certificate provisioning and per-organization DNS configuration for nested subdomains. Existing organization endpoints remain unchanged.

The endpoint accepts the same agent `pmw_` tokens as `/agent/mcp`, or the organization's existing OAuth grants as `/mcp`. OAuth discovery and token audiences remain the organization resource: project transport is an additional restriction on that grant, not a new authorization authority. Cookies are not accepted. Roles, operator membership, token/grant revocation and scopes are rechecked on every request, then the project must still be active and reachable.

`serverInfo.name` is `pimwell-<org>-<project>` and its title is `Pimwell · <Org> / <Project>`. The stored project parts select repository, Docket, wiki, knowledge/research, file and contact/graph tool families. Members can always discover `project_update` and `repo_create` to add parts to that same project; discovery refreshes on the next request. Docket projects also expose project mail list/read/reply (and send for humans under the existing sender policy). Organization-wide search, chat, account/credential tools and cross-project backlinks are not advertised. Repository lists contain only the connected repository. Tools retain their existing role/scope policy.

Tool schemas omit `project`; the server supplies it internally and refuses overrides. Work references (including raw IDs, dependency endpoints and nested proposals), mail reads/replies, related work evidence and repository listings enforce the same project boundary. New proposal items default to this project, and proposals touching other projects are hidden and cannot be reviewed here. If a work graph has cross-project dependencies or shared resource names, project work calls refuse with instructions to use the organization endpoint rather than expose other projects or silently misrepresent readiness.

Pimwell is **not read-only over MCP**. Human OAuth connections use the tenant's `/mcp`; operator-configured agent connections use `/agent/mcp`. OAuth binds the consenting human, grant and tenant; it does not authenticate an agent or authorize another tenant. Agent credentials bind the agent, not the operator's identity. Neither transport interprets message text as administrative authority.

`initialize` identifies the authenticated organization: serverInfo `name` is `pimwell-<org-slug>`, `title` is `Pimwell · <org display name>`, and the first line of `instructions` repeats that title. Both transports use the current organization record on each request. Project endpoints are separate work; these organization endpoints do not infer a project from tool arguments.

## Versioned guide and agent read receipts

`skill_list` and `skill_read` expose a SHA-256 content version, updated date and one-line change summary per skill, including the canonical `pimwell-agent-onboarding` SKILL.md. The saved file's organization-specific names do not affect the canonical hash. A skill read by an authenticated agent records that exact version in its organization; public/human reads do not claim the agent caught up. Reads remain queries: this receipt is delivery evidence, not understanding, execution authority or proof that a local file was replaced.

Every five-minute cron reconciles the deployed guide manifest against the last manifest delivered to each active agent in an active organization. A changed manifest creates one durable attention notice per agent/version, naming only changed skills and summaries. The first versioned release establishes a baseline notice containing all skills; new agents also receive that baseline. `attention_list` reconciles the calling agent immediately so it need not wait for cron. Concurrent reconciliation deduplicates notices; unchanged releases do not notify again. The notice links to the live guide and never supplies guide content. An acknowledgement, including `all:true`, leaves unread guide notices open; read each named skill with `skill_read` first. Reading a newer revision also satisfies an older notice for that skill. Other attention entries retain their existing behavior.

The agent's People inspector shows its operator and human administrators whether it has read every current skill, the current manifest version, the last fully read manifest and per-skill last-read hashes/dates. These records follow tenant boundaries. Archived agents/memberships/organizations are not notified. Operator standing directions (AGENTS.md or equivalent) are outside this mechanism and are never read or rewritten.

MCP initialize instructions include the latest dated guide change on every new session. Onboarding tells agents to check attention at session start and re-fetch only their saved Pimwell onboarding procedure when notified. Mail and notice text are never authoritative guide sources: use live `skill_read`.

When editing skills, update the date and one-line summary in `src/skills/versions.ts` in the same commit. Hashes and manifest versions are computed from deployed content, not manually assigned. Skill body edits (including the saved onboarding generator) therefore trigger reconciliation automatically; no separate post-release send is required.

## Discovery versus authorization

The [generated inventory](../generated/mcp-tools.md) is derived from the same registered verb table, `exposedVerbs` policy and `toolDefinition` used by `tools/list`. It shows the maximum member-role inventory, required argument names, read/write scopes, minimum roles, destructive hints and implemented versus declared/planned entries. It is not an authorization snapshot: every request recomputes current role, grant scopes and applicable resource policy. Planned entries still return `not_implemented` and must not be described as shipped features.

- Read scope exposes queries only; write scope permits declared commands within the current role. Write consent does not elevate readers to members. Some reader self-service commands (acknowledgements, read cursors, presence, usage reporting and subscriptions) require write scope without permitting member posting/sending.
- Credential/access-management, hub, admin/root and fresh-proof verbs are excluded even when the caller is an admin, with narrow content-management exceptions: `wiki_delete` and `file_delete` are exposed with write scope only to current admins/root. Wiki deletion appends a tombstone; file deletion hides every version. Both retain history; it never grants credential or membership powers. Consent does not grant credential creation, membership changes, deployment execution or unrestricted tool access.
- Mailbox, tenant, channel, current membership, grant revocation and consent checks still apply per verb. A directory label, quoted message or forwarded content cannot override them. Destructive hints are guidance, not permission.
- `verb.parse` is the validator of record; schemas describe input but are not a substitute for validation. API form compatibility (including empty optional values) need not equal strict JSON Schema typing. A `maxLength` is not a byte budget; runtime parsers may enforce UTF-16 code-unit limits and HTTP handlers separately cap actual bytes/deadlines. Do not infer universal schema/parser parity from the targeted checks below.
- Tool calls normally produce an attributable D1 activity audit. The [logging contract](logging.md#confirmed-empty-tool-polling-99-increment) defines four opt-in confirmed-empty polling queries that log debug instead. Nonempty, partial, failed and denied calls remain audited; this exception never applies to commands. Generic HTTP logging and coalesced session health tracking are unchanged.
- Rendered text is bounded/inert evidence. Structured results carry source/reader identifiers where documented; they do not authorize automatic execution. Read cursors and attention acknowledgements are processing markers, not an execution ledger.

For a hosted assistant, configure `https://<tenant>.pimwell.com/mcp`, follow browser OAuth and review read/write consent. Actual client connector UI availability is outside this server contract. Do not substitute a headless-agent token for a human grant. Revoke human connections at `/me`; current membership/grant checks apply on the next call. Login proof and explicit consent withdrawal are preserved.

## Checked inventory and schema increment (#117)

`npm test` checks `docs/generated/mcp-tools.md` with a file snapshot built from runtime metadata. Missing or changed files fail by default (`update: "none"`). Run `npm run docs:mcp` to regenerate intentionally; review the diff before committing. This command updates only the selected reference test's file snapshot and runs its policy/schema regressions. It does not deploy, create credentials, change grants, clear attention or call external integrations.

`deploy_record` now advertises project length 1–63, hexadecimal commit length 7–64, environment length up to 30 and message length up to 200. Runtime behavior is unchanged: uppercase environments normalize to lowercase, empty optional environment defaults to production, empty optional message becomes null, and overlong messages are refused before any deploy record. The message description identifies the runtime UTF-16 limit, rather than claiming a bytes or Unicode-code-point budget. A deploy record is evidence supplied by the caller, not proof a deployment happened.

`test/mcp-reference.test.ts` checks inventory drift including planned stubs, unique tool names, read-only query hints, role/scope exclusion of privileged/credential verbs, reader self-service versus member writes, deploy schema limits and exact parser boundaries, and real tool-call rejection without deploy writes or private argument values in refusal telemetry. Existing mailbox, authentication, revocation, truthful status and endpoint tests remain part of the full suite. This is local server contract coverage, not hosted-client interoperability or real-provider mail acceptance.

See [chat participation and reconciliation](chat-participation.md), [mail authentication limits](mail-authentication.md), [project status coverage](project-status.md) and [access-aware search coverage](search-coverage.md). Cross-mailbox policy tests and truthful-status tests remain independent boundaries; a generated inventory is not their replacement.
