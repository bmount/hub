# Explicit channel presence increment (#132)

## Contract

- `POST /api/chat.heartbeat` accepts `{ c, status }`, where status is `online`, `away`, or `offline`. It publishes **only the authenticated caller's identity** in an active channel the caller can read. No client-controlled identity, TTL, timestamp, session label, or free-text status is accepted into stored presence.
- `POST /api/chat.presence` accepts `{ c }` and returns channel-scoped recent explicit heartbeats, server `observed_at`, `last_seen` (last heartbeat, not last message/read/work), `expires_at`, and derived state. Query/post/page loads never publish or renew presence. Missing entries are **unknown**, never inferred offline.
- Online/away expire after **90 seconds**, becoming **stale** at the exact boundary. Explicit offline is distinct from stale: it is the caller's reported status, not proof that every client/device is disconnected. Heartbeats do not prove the agent is doing work or the human is reading.
- State is per identity/channel, last heartbeat wins (including multiple tabs/devices). It is not a count of connections. Up to 200 recent identities are stored transactionally in the existing channel Durable Object's KV; no D1 or SQL schema migration or new binding. Reads omit records older than 24 hours; the next heartbeat prunes/replaces bounded stored records. This is not a permanent presence directory or activity history.
- The existing tenant/channel policy applies to both verbs. Agents need an explicit channel grant; humans need organization access. Archived channels refuse both verbs but keep ordinary readable chat history. Read results recheck subject identity and organization membership state and agent channel membership, so retained heartbeats from removed/archived subjects are not exposed. DO binding checks reject cross-tenant/channel reuse.
- Native browser/agent-run API sessions can call these verbs. MCP `chat_presence` requires **read** scope; `chat_heartbeat` requires **write** scope and only publishes the authenticated principal. Both retain reader minimum role and current channel checks; neither joins channels. OAuth, Playground and agent MCP connections use existing exposure rules; read-only grants cannot publish. Long-lived tokens retain their existing API restriction to run/session setup (the separately authenticated agent MCP endpoint retains its own existing token contract). No grant scopes are widened.
- OAuth/Playground heartbeats are stored with authoritative `via_assistant: true` and labeled in query results and browser text, so a helper's report is not silently presented as direct human activity. Agent MCP remains its own agent identity. Native reports reset the flag to false; client-provided identity/provenance flags are ignored. Older KV entries default to false because they predate assistant publishing; no migration is needed.
- MCP text quotes and bounds user-supplied names and carries the data-evidence disclaimer and stale/unknown semantics. Presence calls audit argument **keys only**, never channel/status values or results. A heartbeat is deliberately **not replay-idempotent**: each accepted call is a fresh report, with fresh authoritative time. After ambiguous delivery, query/reconcile rather than blindly retrying or claiming offline was accepted.

## Browser behavior

Active channel/thread pages load a content-hashed external script. Presence publishing is **opt-in for that page** via “Share presence in this channel.” Loading a page polls the query only. Without JavaScript, no heartbeat is published and status remains unknown.

While opted in and visible, a heartbeat/query refresh occurs every 30 seconds. Hiding the page reports away once, then stops renewing online presence; delayed/closed/disconnected tabs expire naturally. Stop-sharing sends explicit offline when possible, while honestly warning that a failed update leaves the previous heartbeat to expire. No unreliable unload/offline delivery is claimed. A back/forward-cache restore requires explicit opt-in again.

Names and status are rendered using DOM `textContent`, not HTML. Cached online/away entries expire locally using a monotonic clock and conservative full request round-trip subtraction, independent of client wall-clock skew. The UI separately shows the server snapshot observation time and a conservative snapshot age, without announcing every age tick through the live region. **Every cached snapshot expires locally after 90 seconds**, including explicit offline and empty snapshots: no successful refresh means current status is unknown, not a permanent offline directory or “no recent heartbeats.” This browser freshness bound is separate from the API's 24-hour recent-record retention.

Fetches are bounded to eight seconds. Disconnect, failed refresh or access denial clears cached activity and says current status is unknown; authentication/permission denials stop publishing and disable the sharing control. Offline/pagehide events clear the UI immediately, abort outstanding transport and invalidate its lifecycle generation. Late successes or denials from an old generation cannot repaint activity, disable a restored page's controls, or continue an old heartbeat into another query. A queued fresh refresh may run after the old request settles; restored pages never resume publishing without renewed explicit opt-in. Aborting a heartbeat is not evidence that the server rejected it; any previously accepted heartbeat still expires normally. Presence queries do not auto-join a channel or clear unread cursors.

Workbench pane replacement emits a scoped `wb:before-replace` lifecycle event. Presence clients in the replaced pane abort/invalidate pending requests, stop timers and unregister document/window listeners before detachment. New channel/thread/refresh panes start unshared, including same-channel navigation and history back. The old channel must never keep renewing while its detached DOM is invisible. No unreliable automatic offline send is claimed; the last accepted report expires normally.

Delayed transport deliberately delivers responses even after abort, checking that lifecycle-generation guards suppress stale successes/denials and post-heartbeat continuations. `test/verb-table.test.ts` pins access and verifies no author-like input enters parsed parameters.

`test/chat-presence-mcp.test.ts` runs actual HTTP MCP/OAuth/Playground calls: own identity/time/provenance, schema/scopes, missing and invalid status denial, channel and tenant isolation, revoked subjects/viewers, archived channels, content-free audit, bounded inert names and no message/wake/cursor effects. Exact exposure lists and verb metadata are pinned in existing MCP/table tests. Shipped-JS regressions also cover assistant labels and detached-client disposal with delayed responses.
