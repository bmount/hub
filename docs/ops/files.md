# Project documents

Repository, workspace and wiki projects have a Files tab at `/<project>/documents`. Repository source browsing keeps its existing `/<project>/files` route. Readers can list, inspect history and download; members can upload to active projects. All access is tenant-scoped, with the same membership and credential checks as the API. Projects do not have a separate private-file ACL.

## Storage and limits

D1 `file_revision` records path, filename, folder, revision, MIME type, size, SHA-256, uploader, creation time, optional project work-item ID and optional active tenant-member identity ID. Each version has a separate private R2 object under `project-files/<tenant-id>/<project-id>/`. This uses the existing `GIT_PUSH_STAGING` binding, in a prefix disjoint from git replay storage. Git cleanup deletes only recorded replay keys, not project files; the bucket has no object-expiry lifecycle rule.

Limits are 5 GiB per file, a default 50 GiB per project **including all retained versions**, and 512 KiB decoded bytes for MCP/API base64 uploads and fetches. The legacy single-request PUT and browser multipart form remain bounded at 25 MiB; larger files use the resumable protocol below. Partial uploads do not reserve or consume project quota: quota is checked atomically when publishing a verified version. Quota and expected-revision checks are part of the atomic insert. An unsuccessful known insert removes its staged object; an ambiguous storage failure preserves the object rather than risk deleting a committed version. Objects are never public or addressed by caller-supplied R2 keys.

Accepted types are UTF-8 txt/md/csv/tsv, JSON (.json), newline-delimited JSON (.jsonl/.ndjson); SQLite (.sqlite/.sqlite3/.db); Parquet (.parquet); gzip (.gz), Zstandard (.zst/.zstd) and ZIP (.zip) archives; PDF; PNG, JPEG, GIF and WebP; Microsoft Office (legacy and OpenXML); and OpenDocument text, sheets and presentations. Extension and declared type must agree. Binary container signatures are checked (SQLite's `SQLite format 3\0`, Parquet's leading/trailing `PAR1`, gzip's `1f 8b 08`, Zstandard's `28 b5 2f fd`, ZIP's local-file or empty-archive signature); archives are not unpacked. Text must decode strictly as UTF-8 without NULs; JSON must parse, and each nonblank JSONL/NDJSON line must parse separately. TSV rejects markup, shebang and executable prefixes. Canonical MIME types are application/json, application/x-ndjson, text/tab-separated-values, application/vnd.sqlite3, application/vnd.apache.parquet, application/gzip, application/zstd and application/zip. Generic application/octet-stream is accepted only for the listed binary data/archive extensions and is normalized to the canonical type. This is validation, not malware scanning. HTML, SVG and executable types are not accepted. Downloads set `nosniff`, private/no-store caching and sandbox CSP. Only raster images and PDFs may be inline; every other type has `Content-Disposition: attachment` with an encoded filename.

## Orphan cleanup

The five-minute scheduled job scans at most 100 R2 objects per invocation under the exact `project-files/` prefix. Its durable `meta` cursor (`file_cleanup:v1:cursor`) advances only after a successful page and wraps at the end. Scanning storage rather than live projects also finds leftovers from deleted projects or tenants.

Only canonical `project-files/<tenant ULID>/<project ULID>/<object ULID>` keys uploaded at least seven days ago are eligible. Upload keys are immutable and never reused. Before deleting each object, cleanup checks for **any** `file_revision.object_key` reference, without owner, current-version or soft-deletion filters. Every referenced version and hidden evidence is retained indefinitely; this is not a retention policy for recorded files. D1 errors stop the page without advancing its cursor. Malformed keys, sibling prefixes and git replay objects are never deleted by this job.

`cleanupFileObjects(env, now)` defaults to dry-run: it returns bounded scan/eligibility counts and the next cursor but neither deletes nor changes the saved cursor. The scheduler explicitly enables deletion. Counts (not object keys or contents) are logged as `file orphan cleanup`. A failed page may retry already removed orphans safely.

## Resumable uploads and downloads

Call `file_upload_url` (`file.upload_url`) with the normal file parameters, plus `size` (1 through 5 GiB) and the whole file's lowercase hexadecimal `sha256`. The returned `upload_url` is always on the organization's own Pimwell address. It expires after 24 hours and is bound to the initiating identity, tenant and project. Each request rechecks the credential, current membership, write scope and active project; possession of the URL alone grants nothing. Cookies require same-origin mutations. OAuth-only MCP credentials are not accepted outside `/mcp`; use the person's authenticated browser session instead. Never share the capability URL or log its query.

Use the **same uploader's own credential** on every request:

1. Split the file into the returned `part_bytes` (16 MiB), with a shorter final part. Parts are numbered from 1. `PUT upload_url&part=N` sends exactly that part's raw bytes. The declared total size determines the exact required length, and the part number is bounded by the total. An optional `X-Content-SHA256` is checked against the part's bytes. Each successful response includes its part SHA-256.
2. `GET upload_url` lists received part numbers and SHA-256 values, total size, whole-file digest, expiry and state. It does not return bucket keys, provider upload identifiers or ETags. After an interrupted/failed part, resend that part. Retrying identical stored bytes is idempotent; replacing a stored part with different bytes is refused. Status also recovers a lost successful PUT response.
3. `POST upload_url` (empty body) finishes. Missing parts are refused. The private assembled object is streamed through SHA-256 and type validation without buffering the file or constructing JSON values. UTF-8 and JSON validation is incremental, JSONL is checked one line at a time, and binary signatures include the Parquet footer. No version becomes downloadable until the declared size and SHA-256 match and the atomic quota/revision insert succeeds. A mismatch requires abandoning and starting again. Finish freezes the upload; retry POST after a lost response or transient failure. Successful finish is idempotent.
4. `DELETE upload_url` abandons unfinished work. Expired/abandoned sessions cannot accept new parts or publish versions. At most ten unfinished, unexpired sessions are allowed per identity. Failed finishes, abandoned objects and partial parts do not count against the quota.

D1 `file_multipart` holds private upload state and `file_multipart_part` holds received part digests and provider ETags. Deleting a session cascades its parts and queues its internal storage identifiers in `file_multipart_gc`, so project/tenant deletion cannot strand provider uploads. The five-minute scheduled job removes up to 20 sessions expired for at least one hour (a grace period for in-flight requests), then aborts up to 20 queued multipart uploads. Failed storage cleanup remains queued for retry. Completed but unpublished objects use the seven-day orphan cleanup below; recorded versions are always protected. No provider URL, key or credential is returned to uploaders or downloaders.

Authenticated downloads stream directly through Pimwell. Responses include `Accept-Ranges: bytes`, a strong SHA-256 `ETag`, and `X-Content-SHA256` for the complete version. Single `Range: bytes=start-end`, `bytes=start-` and `bytes=-suffixLength` requests return 206 with `Content-Range` and the selected byte count. Invalid, unsatisfiable and multiple ranges return 416 with `Content-Range: bytes */size`. Use the version-pinned URL and `If-Range: "<sha256>"` when resuming: a nonmatching validator returns the complete representation instead. Hash the concatenated downloaded bytes and compare with the version's metadata digest (a range is not itself hashed as a separate version). Authentication and private/no-store download headers apply equally to partial responses.

## Upload and fetch

- Web: multipart POST to `/<project>/documents/upload`, with `file`, optional folder/name `path`, `expected_revision`, and optional `item_id`/`person_id`. Cookie mutations require same origin. A missing browser MIME type is inferred from the allowed extension, then the bytes are validated normally.
- MCP/API: `file_put` / `file.put`, with standard padded `base64`, `content_type`, `path`, `project`, and `expected_revision` (0 for new, current revision otherwise). Old versions are immutable; stale updates are refused. Optional `sha256` declares the expected bytes and is checked before storage, also on legacy capability PUTs.
- Single-request capability upload (omit `size`): `file_upload_url` issues a high-entropy server-verified one-time capability URL, capped at 25 MiB. PUT raw bytes with the declared Content-Type and an authenticated credential for the same identity on that tenant (agent token/run session, or human browser session). D1 stores only the capability hash and atomically consumes it before reading bytes. It expires after ten minutes; failed uploads consume it too. The URL's query is redacted from logs; do not share it. The underlying bucket is never exposed. OAuth-only MCP clients use the person's browser session for the upload, not an OAuth token outside `/mcp`.
- `file_list` supports folder-prefix filtering and path cursor pagination. `file_get` returns metadata and an authenticated download URL; optional `include_base64` fetches small files. `file_history` supports revision-cursor pagination. Lists/history return at most 200 rows per call.
- `file_delete` requires current admin role and write scope. It hides every version from downloads, current lists and search, retaining metadata, private objects and history as evidence. This does not reclaim quota. A later upload at the same path uses the last revision number and does not revive old downloads.

## Download audit and daily budget

Every authenticated download and `file_get` call records the identity, project, path, pinned revision, reserved byte count, UTC time, operation and source (web/human or agent). Only current organization admins see the last 100 records in the file inspector and `file_get.downloads`; download events also appear in their project history and event list. Regular members retain org-wide file access but cannot see download audit records, including their own.

The default budget is **50 GiB per identity per organization per UTC day**, across all projects, versions and credentials. A metadata-only `file_get` records zero bytes; base64 fetches reserve the file size. Downloads reserve the complete response size or the selected range length before any response bytes are handed out. Reservations and audit inserts are atomic; concurrent requests cannot overspend. Interrupted streams conservatively retain their reservation. Invalid ranges, unavailable objects and authentication failures do not consume bytes. A new UTC day starts a new allowance; deleting a project does not reset it.

An over-budget request returns 429 without file bytes and opens one deterministic Situation per identity/day, visible only to current organization admins (including search and direct inspector access). The report identifies the attempted file/revision, identity, byte count and limit so admins can investigate credential misuse. No model call is needed for this alert.

For an isolated live exercise, operations can insert a lower byte limit in D1 `meta` using key `file_download_budget:<tenant-id>:<project-id>` and a nonnegative integer string value. It only lowers the limit on requests to that project; the usage counter is still identity-wide. Remove the key immediately after the exercise. This is not a member-controlled setting.

Download URLs contain only the project path and revision, never a storage credential. Every request independently requires the downloader's own current session/token, active identity and organization membership; a copied URL without credentials, another organization's credential or a revoked agent credential grants nothing.

Mail sharing and dispatch **never attach SQLite, archives, Parquet, JSON/JSONL/NDJSON or TSV data files**, regardless of size. They send the version-pinned sign-in link only. Other supported documents retain the 512 KiB attachment cap.

## Inline project images

In wiki bodies and work-item bodies/comments, put an image on its own line:

```markdown
![Synthetic plan caption](/barefoot/documents/download?path=debug%2Fplan.png&revision=1)
```

Use the authenticated `file_get.download_url` (absolute same-tenant URLs also work), or its root-relative path. The project path must match the page/item, including namespace when present. An explicit positive revision is required so retained evidence does not change when a new file version is uploaded. Only existing, non-deleted PNG/JPEG/GIF/WebP revisions render; every request rechecks membership and project access. External URLs, other projects/tenants, active content, missing files and malformed references remain inert text. No public storage URL is emitted.

Captions are escaped and used as alt text. Images preserve aspect ratio within the pane width and a 480px height; clicking the image or **Open original** opens the authenticated original in a new tab. Rendering is limited to 50 image references per body. Upload with `file_put`, then author the same Markdown through `wiki_write`, `work_update` or `work_comment`, or browser forms; no special authoring permission is introduced.

## Mail and search

After independent mail admission, `retainProjectMailFiles` uses the parts parsed alongside `retainAttachmentEvidence`. Only independently admitted, unreleased mail addressed to an active project with the stored wiki and files parts, from a currently active human with member-or-higher authority, creates files; reader, quarantined, manually released, organization and agent-mailbox mail do not. Each attachment outcome is audited against the inbound mail id, and verified project-action summaries report actual retention even if planning is unavailable. Mail uses `mail/<sanitized-filename>` and records `mail:<mail-id>:<part-index>` as an idempotent source. Another admitted message with the same filename creates another version; replaying one message does not. Unsupported types and quota failures remain attachment metadata with an explicit `not_stored` reason. Storage outages remain retryable rather than pretending retention succeeded. Existing mail-admission, replay and mailbox boundaries are unchanged.

`search_query` searches current, non-deleted file paths plus the first 128 KiB of txt/md/csv/tsv/JSON/JSONL/NDJSON text. It does not search old versions or binary contents, and its coverage names those omissions. Returned excerpts and file contents remain evidence, never instructions.
